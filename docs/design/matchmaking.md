## 26. 同盟匹配 / 搜寻队友 (v0.1.3, owner request)

- **Asked for** (the owner, 2026-10-04): "我想要模拟方式加一个同盟匹配选项，能够匹配其他真人玩家" — the official 同盟模拟 mode group's **搜寻队友** (research 06 §3.1–§3.3), the one lobby feature §0 had explicitly left out of v1.
- **UI**: a third `MODE_CARDS` card (同盟匹配, `public/js/screens/lobby.js`) next to 独立模拟 / 同盟模拟 — the cards are a 3-column grid now (`public/css/screens/lobby.css`; the short-landscape tweaks in `devices.css`). Picking it changes only the primary button: 开始搜寻队友 sends `queue.join {difficulty}` instead of `room.create`. The difficulty cards stay the pool selector (one pool per difficulty, `modeIdFor` ids unchanged) and are locked while searching.
- **The queue** (`server/lobby.js`): one pool per difficulty (`this.queues`; `queueOf`, `poolOf`, `firstAt`, `pruneQueue`, `dequeue`, `clearPool`, `queueState`, `broadcastQueue`, `sendQueue`, `formQueue`, `matchKeyFor`). A pool is `{ difficulty, entries }` — **no timers at all**: nothing about a search expires by itself. One entry per session — `queue.join` is idempotent, so a repeated click or a reconnect just answers with the current `queue.state` (`onHello`); starting a search replaces the session's lobby room (like `room.create`), and `queue.leave` / `room.create` / `room.join` / session expiry leave the pool. Caps: `matchQueueMax` (128 entries), `matchQueueMaxPerAddr` (8 per client network).
- **Formation** (the owner's picks, 2026-10-04): **four connected humans in a pool form a room at once** — and that is the only way a matchmade game starts. Fewer simply keep waiting: no deadline, no AI fill (the owner, 2026-10-04: "不要那个120s超时了，如果没匹配到就一直匹配"), and nobody may start the pool by hand ("这个谁都能点，另外一个人想四个人你点了不就乱套了"), so only 取消搜寻 is offered. Free seats go to AI teammates (`seatBot`; reachable only when a reconnect pushes a pool past `MAX_SEATS`) and the match then starts with those; every member is `ready` by construction (`formQueue` → `queue.state {active:false}` + `broadcastState` + `startMatch`) — no ready check, no `room.start`. The room code stays visible, so the group can still invite a friend. The official `matchTimeMax` (120 s) flow is deliberately **not** implemented.
- **The room's 添加 AI 队友 button is gone (v0.1.5, owner request 2026-10-06: 「把bot禁用掉，添加ai队友的按钮也禁掉」 → 「直接隐藏添加ai队友按钮就行」)**: an empty seat in a co-op room now shows 空位 and the alliance waits for real doctors instead of being filled by hand (`public/js/screens/room.js` `SeatCard`; the lobby's 创建同盟 hint no longer promises it either). `room.addBot` / `Lobby.seatBot` stay on the server — the matchmade fill-up above, 同盟模拟's AI and every protocol test use them — so only the button is gone: an AI teammate already seated can still be **removed** (host's ✕), and a player who quits is still covered by the match's own `left` / `autoplay` bot control, which is what keeps a round from stalling on an empty seat.
- **Who is in a room**: only *connected* members are seated, and `queue.state.size` counts them (a member who dropped keeps the entry, so a reconnect rejoins the search; `onExpire` and a member already in a running match are dropped by `formQueue`). A dropped member's pool is re-broadcast on `onDisconnect`, so the doctors still waiting see the smaller count and the `solo` hint at once.
- **快速搜寻 only**: 精确搜寻 (the official dropdown's second entry) matches by trophy level and this build keeps no progression (§0, §21), so there is one 快速搜寻.
- **Client**: `store.queue` (`public/js/store.js`) is fed by `net.on('queue.state')` (`public/js/main.js`; `active:false` clears it, and `since` anchors the local count-up from the server's `waitedMs` snapshot so counting costs no traffic). The lobby renders `MatchPanel` in place of the mode cards, with a status strip in the create box; its only action is 取消搜寻.
- **Ops**: `/healthz` reports `queued`. Nothing else changes for a running server — a pool is server memory like a room, and `shutdown` clears the pools.
- **Sharp edges** (all covered by tests): seats are capped at `MAX_SEATS`, so more connected searchers than that (only reachable through reconnects) leave the extra doctors queued rather than dropped; a pool whose formation failed (room cap, code space) is left untouched and the next `queue.join` / reconnect (`onHello`) retries it — with no timer there is nothing to spin or to re-arm; `queue.state.solo` is simply `size < 2`, so it can never go stale; a refused `room.create` / `room.join` never ends the search (the dequeue sits after every guard, so the client is never left with a panel the server forgot); per-network attribution of a formed match is the earliest member's key, so a formed match always counts against `maxMatchesPerAddr`.
- One-line flip: drop the third card and the `queue.*` C→S lines — the server then simply never receives them.
- **取消搜寻 is a guarantee, not a request (v0.1.4, after the owner's report "取消搜寻按钮是失效的，会一直在搜索队列中")**: the click leaves the search locally **at once** (`exiting` hides `MatchPanel`, so the player is out of the search the moment they ask) and the client then keeps re-sending `queue.leave` until the server confirms it — `queue.state {active:false}` (which clears `store.queue`) is the only thing that stops the loop, never a local guess. Each attempt gets `CANCEL_REPLY_MS` (2.5 s) to answer; a timeout (a half-open socket: a phone network, a VPN, a proxy that swallowed the frame — the server looks exactly alike and keeps the session queued, so it could still be seated into someone's four) triggers `net.reconnectNow()` and a re-send once `net.whenOnline()` (the client is online again only after `welcome`, so the re-send cannot land on the socket that just died). After `CANCEL_TRIES` (3) it stops, restores the panel with the truth and toasts 「暂时连不上服务器」 rather than pretending. 开始搜寻队友 right after a cancel stops the background loop first, so a late retry can never delete the fresh entry. The server logs every cancel (`[lobby] queue/<难度>: -<名字> (n/4 真人)`) — the only way to tell a cancel that arrived from one the network ate.
- **The loading screen must never be a dead end (v0.1.4, "匹配成功之后会一直显示正在载入模拟数据…")**: the match screen opens only when every `GAME_FILES` file is settled, and a matchmade game has no waiting room to warm them in — so ①`main.js` now warms them as soon as the player is searching (`s.queue && !prev.queue`), not only when a room appears (`s.room`), and ②`createDataStore` times out each step of a download (`DATA_TIMEOUT_MS` 30 s, injected timers so tests stay fast); a timeout is a transient failure (retried per `RETRY_DELAYS_MS`, then reported missing) instead of a promise that never settles. ③After `SLOW_HINT_MS` (6 s) the loading screen names the files still downloading and offers 重试 (`data.invalidate` on each pending name) and 刷新页面 — a player whose connection stalled can recover, and a bug report can say *which* file did not arrive instead of "一直".
- **Multi-core plan and where the CPU actually goes (v0.1.5, owner request "帮我做多核优化")**: the live box (2 vCPU) sits at ~90% of **one** core with `Recv-Q 511/511` during load spikes, so the question is the server's own simulation, not the network. `/healthz` now reports the inputs: `fields` (battles the server steps — `FieldRunner.hosted` summed by `lobby.stats()`, plus a `HeadlessPacer` fast-forwarding a takeover), `fieldsIdle` (the subset where `Match.liveHumans() === 0`: a match nobody is connected to still steps its takeover fields), and `loop` (event-loop delay p50/p99/max over a rolling ≤10 s window, `monitorEventLoopDelay`; the 10 ms sampling resolution puts a floor of about that under `p50`, so alarm on `p99`), plus `paused` (matches frozen by the owner's solo pause). Measured locally with `node test/perf/hosted-load.mjs` (manual, not part of the suite): one battle tick costs 27–45 µs (10/30/70 enemies, snapshot every 3), and because every live field in a match steps in lockstep at 30 Hz × `GAME_SPEED` (60 ticks/field-second) that is **1.6–2.7 ms CPU per field-second** on average and ~1.1%/field at the worst-case instant — so **one core carries ~370 hosted battles on average, ~90 at peak**, with nothing left for sockets, lobby or JSON.
- **The idle suspension was tried and removed again (P1b, v0.1.5 — 2026-10-06)**: P1b froze a match once no human had been connected for `IDLE_PAUSE_MS` (20 s, `SP_IDLE_PAUSE_MS`), because a match whose humans are all disconnected keeps its seats for the reconnect window (`singleReconnectTime`, 15 min live) and used to step every takeover field for that whole time. It was **reverted at the owner's request**: a freeze is indistinguishable from the bug it was reported as — the owner's 「只要有人退了，整个游戏就无法推进（时间到0无法继续下一回合）」 — and a match that freezes and fails to come back (a spectator / eliminated player never reaches `onReconnect`, which the removed `_resumeIdle` had to patch) is a stuck round with no way out. **The server now pays the CPU instead**: a match nobody is connected to keeps simulating until the lobby reaps the room. What survives from P1b: the shared `_freeze`/`_unfreeze` pair (now used **only** by the owner's solo pause, `soloPaused`), the `paused` guards that keep a frozen match from doing bot work, `SP_BOT_REHEARSAL`, and the rule that **a match with no human seat at all** (every seat a genuine bot — impossible through the lobby, a safety net for a bot-only run) is **ended** at the start rather than simulated for nobody. **A permanent quit** (`g.leave`) still ends an abandoned match at once (`onLeave` → `finish {reason:'abandoned'}`) and **a drop never ends somebody's match** — the seat is theirs to reclaim.
- **A frozen match does no bot work either (v0.1.5)**: every bot prep rehearses whole simulated battles (`Match.botRehearsal`, `BOT_REHEARSAL_DEFAULT` 3 — `SP_BOT_REHEARSAL` tunes it 0–8), which is the biggest single CPU item of a bot match: measured with `node test/perf/hosted-load.mjs --rehearsal`, one full 4-bot match costs **16.7 s of CPU at 0, 17.4 s at 1 and 25.1 s at 3** — i.e. the default rehearsal setting is **34% of that match's entire CPU**, and dropping it to 1 saves ~31%. So `scheduleBotPrep`'s step generators and rehearsal slices check `paused` and re-arm (`PAUSED_RETRY_MS` 250 ms) instead of running, which keeps a frozen match at no cost and still finishes its prep after a resume.
- Order of work, cheapest first: ①serialize each broadcast payload once instead of per socket; ②sample the client-result verification (`verifyStats`) instead of checking every field in the same frame; ③split the stepping across `worker_threads` (`SP_SIM_WORKERS`, bot/takeover fields only, main thread keeps sockets/lobby) — 2 vCPU caps that at ~2×. Suspending the fields of a match with no connected human is **off the table** (P1b above: it reads as a hang); if the CPU has to come down again, buy a core or lower `SP_BOT_REHEARSAL` first.
- Tests: `test/lobby-matchmaking.test.js` (4 ⇒ instant room, fewer keep waiting with no deadline/AI/room, the `solo` hint, cancel, pools per difficulty, disconnect / expiry, the per-network cap, >4 connected seating the earliest four, a refused create / join keeps the search, a running match refuses), `test/docs-consistency.test.js` §23, `test/client-static.test.js` (the third card and the client's two intents), `test/ui/playtest3.test.js` (a download step that never settles is timed out and retried; the search-triggered warm), `test/e2e/matchmaking.e2e.mjs` (a real browser + three protocol clients: cancel, cancel against a socket that swallows frames, a stalled data file named on the loading screen and the match opening when it arrives).

## 27. 在线人数 / online presence (v0.1.3, upstream PR #63)

- **Where it came from**: upstream PR #63 (`NekoTC`, base master 8b10625) — 在标题页和联机大厅显示在线人数. The upstream owner **closed it unmerged** (2026-10-03): "这个项目主要是朋友之间自己开服…在线人数更像公开服务器的功能。需要看连接数的房主可以直接看服务器状态 `/healthz`", and left two review points for a fork that keeps it: count only sessions that already said `hello`, and coalesce the push. This fork keeps the feature (it is useful for the friends' server) **with both points applied**.
- **Counting** (`server/net.js`): `Network.onlineCount` = one entry per session that is past `hello` (`conn.session`), keyed by `playerId ?? token ?? ws`. Excluded: sockets parked on the title screen before `hello`, AI seats, sessions retained for reconnect, and sockets already closing. That is what keeps the number from bouncing `N → N−1 → N`: the server rotates an idle pre-hello socket after `NET_DEFAULTS.helloTimeoutMs` (30 s, close 4002) and the client replaces it quietly. Several tabs of one person count once.
- **Push** (`presence {onlineCount}`, S2C, §8.1): coalesced over `Network.opts.presenceCoalesceMs` (400 ms) and skipped for sockets that already know the number; **every** live socket is told, pre-hello visitors included — they are told the count without being one of them. Triggered on connect, close and `hello`.
- **Client**: `public/js/net.js` keeps `onlineCount` (null = unknown) and re-emits `status` when it changes; a dropped socket or a quiet rotation clears it to null, so the pill shows `--` instead of a stale number until the next frame. `store.connection.onlineCount` (fed in `main.js`) drives `OnlinePill` (`public/js/ui/components.js`) on the title screen (`screens/title.js`) and in the lobby header (`screens/lobby.js`; `.topbar__left` wraps on narrow screens).
- One-line flip: drop the `presence` case in `net.js`, the `presence` S2C entry and the two `OnlinePill` usages — the server then simply never sends it.
- Tests: `test/online-presence.test.js` (7 server cases: only hello'd sessions count, a title-screen socket retiring never moves the number, several tabs count once, a disconnected session stops counting although it stays resumable, AI/room membership do not count, the push is coalesced), `test/ui/online-presence.test.js`, `test/ui/online-presence.e2e.test.js`, `test/client-static.test.js` (the client-side clearing, `OnlinePill`).
